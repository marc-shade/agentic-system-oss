# Bet: Maximum Scrutiny Mode

**Usage**: `/bet [claim or question]`

**Examples**:
- `/bet This architecture is optimal for our scale`
- `/bet Our caching strategy prevents all race conditions`
- `/bet This code is production-ready`
- `/bet The authentication flow is secure`

---

## Activated: Maximum Quality Gates

Let's bet $100 on: **{{args}}**

Imaginary money = real thoroughness.

## Quality Gate Pipeline

### Gate 1: Introspection
**Self-assess your reasoning quality**:
- What assumptions am I making?
- Where might I be wrong?
- What don't I know that I don't know?

### Gate 2: Confidence Scoring
**Assign confidence % to EVERY claim**:
- Each assertion gets a number (0-100%)
- Identify low-confidence claims (<60%)
- Either strengthen evidence or hedge appropriately

### Gate 3: Adversarial Review
**Play devil's advocate**:
- What would a security researcher find?
- What edge cases did I miss?
- What happens under failure conditions?
- Where would a competitor attack this?

### Gate 4: Verification
**Test your claims**:
- Can you prove this with evidence?
- Does the code actually do what you claim?
- Have you tested edge cases?
- What does the data show?

### Gate 5: Concession or Defense
**Final synthesis**:
- Defend the claim with evidence, OR
- Concede specific weaknesses
- Hedge where confidence is low
- Recommend verification steps

## Output Format

Structure your response as:

1. **Initial Assessment** (your first reaction)
2. **Introspection Results** (what you discovered by questioning yourself)
3. **Confidence Scores** (for each major claim)
4. **Adversarial Findings** (what could go wrong)
5. **Verification Status** (what you tested, what you didn't)
6. **Final Verdict** (defend or concede, with confidence %)

## Production Integration

This maps to your **PRODUCTION-ONLY POLICY**:
- No fake implementations
- No "this should work" without testing
- No untested edge cases
- No security vulnerabilities

The /bet command makes quality gates explicit and mandatory.
